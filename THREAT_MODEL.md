### The residual worth naming: T15 is a docstring, not a control

The default is now `RAW`, and every library path always was. But `valueInputOption` remains a
tool parameter, so `USER_ENTERED` is one argument away, and what stands between an injected agent
and server-side formula evaluation is the tool description telling it not to:

> DO NOT pass `USER_ENTERED` for anything derived from document or comment content.

That is an *instruction to the model*, on a surface whose whole premise (T2) is that third-party
content can instruct the model. The same lesson this project wrote down as invariant #10 — *a
type is not a contract with the model; the description is* — cuts the other way here: a
description is not a control either.

Refusing `USER_ENTERED` unless an operator names a capability would make it one. That is a
capability-model change and belongs with **#195**, not smuggled into an adoption commit. Recorded
here so the gap is visible rather than implied by a status of `mitigated` it has not earned.

### What has *not* changed

**T1 is carried forward unchanged**, as #197 required: `CSA_GW_ALLOWLIST_READ="*"` remains a
deliberate interim posture with a documented 1.0.0 path, not a defect, and it is scored
`risk_accepted` on that basis. **T2 is unchanged** and remains the highest row — it is the
project's named primary risk, and none of the work above narrows who decides.

The nineteen rows not listed in §0 keep the audit's status. Absence from that table means *not
addressed*, not *checked and fine*.


## 1. System context

`csa-google-workspace` is a Python library plus a bundled local MCP server for reading and mutating comments and content on Google Docs, Sheets, and Slides. At the reviewed revision (`95c6afa`, v0.28.0) it is roughly 8,500 lines across 53 modules under `src/csa_google_workspace/`, with about 9,900 lines of tests; Apache-2.0, published on PyPI, maintained by Cloud Security Alliance. Four runtime dependencies (`google-api-python-client`, `google-auth`, `google-auth-oauthlib`, `defusedxml`), with `mcp>=2.1` and `openpyxl>=3.1` behind extras. The architecture has two axes — comments are uniform across file types (one Drive v3 API), content is variant (Docs v1 / Sheets v4 / Slides v1) — joined by a `Backend` Protocol seam with three implementations: `ApiBackend` (real Google), `FakeBackend` (in-memory, powers the unit suite), and `PolicyBackend` (the authorization wrapper). Development history is unusual and materially affects this model: 252 commits, effectively one author, with all implementation landing in roughly seven weeks (2026-07-09 to 2026-08-27, v0.1.0 through v0.28.0).

There are **two shipped artifacts with deliberately opposite defaults**, and they are two threat models. The **library** is embedded by developers building agents, review bots, and automations; `Policy.default()` is permissive on both read and modify scope, on the reasoning that `from_credentials` is called by someone who has already decided. The **bundled MCP server** is a local stdio subprocess spawned by an LLM client (Claude Code and Claude Desktop are the named clients), exposing 34 tools, and it fails closed. Both hold the same credential: a persisted OAuth refresh token with full `https://www.googleapis.com/auth/drive` scope — read, write, and delete across the authorizing user's entire Drive, every Shared Drive they belong to, and everything shared with them. Full-Drive scope is **required by design**, since the library opens arbitrary files a user names by URL and `drive.file` cannot reach them; the project is explicit that this forfeits the containment Google's own Drive MCP server gets for free from `drive.file`, and that a software file-allowlist is how it buys that property back.

The risk therefore does not live primarily in the library's code, and `SECURITY.md` says so in its opening sentence: *"That deployment model, not the library's own code, is where the real security surface lives."* The system is a **confused deputy**. Every read surface returns text authored by third parties — comment bodies, replies, `quoted_text`, document and slide text, tracked-change suggestions — and the same agent session holds tools that mutate documents, trash files, grant Drive permissions, and write to the local filesystem, all under the user's own identity. The project names prompt injection through document and comment content as its primary risk and assigns containment to the embedder, while acknowledging that its own bundled server is that risk made concrete. Two prior audits dated 2026-07-22 exist and are cited as evidence throughout this model, but both cover **v0.1.0 — 1,308 lines across 15 modules**. Every module implementing the read-to-act path this threat model is about (`mcp/` and its ten tool modules, `policy.py`, `allowlist.py`, `permissions.py`, `_apply.py`, `_export.py`, `files.py`) was written after those audits and has never been externally reviewed. There are no public advisories against the project and no external security reporters; given a single-author repository with required approving reviews set to zero, that is best read as unexplored surface rather than clean surface.

**Scope of what this model claims, and the control layers it assumes.** Two framings supplied by the maintainer are load-bearing. First, the server grants no authority the user does not already have: the token is the user's own, every action is one the user could perform directly, and there is no privilege escalation anywhere in this model. What the server adds is a *decision path* — a third party who can leave a comment can influence what the deputy does with authority that was never theirs. That distinction, not capability, is the whole content of the confused-deputy frame, and it is why threats here are scored on who chooses an action rather than on what the credential can reach. Second, and more importantly for how this document should be read: **for activities that take place on Google Drive, Google Drive is the correct place to implement policy.** That is where the data lives, where the durable controls live, and where a mature tooling ecosystem already exists. This model does not attempt to reimplement any of it, and treats it as the primary layer.

Three control layers therefore bound every threat below, and this model **assumes the first is in place**:

1. **The Workspace layer — primary, and assumed.** Per-file and shared-drive ACLs, sharing restrictions and target-audience limits, Drive audit logging, version history, retention and backups, Context-Aware Access, and DLP for Drive. This document explicitly assumes the operator has secured their Google Drive such that neither the human nor an AI acting on their behalf can perform actions the organisation would not sanction. Where that assumption does not hold, the ratings below understate the risk, and the remedy is at this layer rather than in this repository. Note one non-uniformity: version history, audit logging and backups are *detective and recoverable*, so they answer integrity and availability threats (T14, T15, T20, T25) without preventing disclosure — a copy an attacker already took cannot be recalled, as the project's own reversibility table says of `file.share`. **DLP for Drive is the preventive exception** and substantially answers T4 by blocking the sharing action itself; it requires Enterprise Standard or Plus, Frontline Standard or Plus, Education Standard or Plus, or Enterprise Essentials Plus, with real-time blocking rather than alerting being Enterprise-tier. It does not reach T7, where an authorized API read is written to local disk and no sharing or download event exists to intercept.

2. **The MCP client layer — externally enforced, and not visible to this codebase.** Two independent controls live here. (i) **Per-tool enablement:** the major clients, including Claude Desktop and Claude Code, let an operator disable individual tools, so any single tool in this server can be removed from the model's reach without touching the server or its configuration. This is not mandated by the MCP specification, so it is client-dependent rather than guaranteed. (ii) **Approval mode:** an operator may require approval for every action, scope approval to a project, or always-allow — and requiring approval for every action mitigates the entire mutation and export surface outright. Both are real and effective. Both share a property with the release-pipeline controls in T19: this repository cannot observe, verify or enforce them, so no threat below is scored as though they are certainly applied. The approval control additionally depends on the accuracy of the server's own tool annotations, which is what makes T7's annotation defect consequential rather than cosmetic.

3. **This server's layer — defense in depth, deliberately narrow.** Ten named capabilities with the three irreversible operations disabled by default and the default line drawn on recoverability rather than on how alarming a verb sounds; four ascending profiles; separate fail-closed read and modify file allowlists matched by file id; no permanent delete anywhere in the library; and a policy that cannot be widened in-band. This layer exists so an operator can broadly switch off classes of action that modify or destroy data, and it does that well. It is not the primary layer and is not intended to be. Consequently the rows that remain highest are the ones the outer layers do not reach: T7, where neither DLP nor the server's own capability model applies, and T3, which is a release-channel threat outside Drive entirely.

**The posture this model is written against.** This project is maintained by the
Cloud Security Alliance — security is the second word in the name — and that is
meant to have consequences in the code rather than in the marketing. Three are
observable in the tree and this model scores them as controls. First, **defaults
are chosen to be safe**: an operator who configures nothing gets the narrow
posture, not the convenient one. Both file allowlists fail closed when unset,
`*` must be typed literally and logs a warning on every parse, the three
irreversible operations are disabled by default, a typo'd profile is a hard
error rather than a fallback to something wider, `Scope.everything()` and
`Scope.nothing()` are kept as distinct representations specifically because
collapsing them is how a fail-closed default turns fail-open during a refactor,
and there is no permanent delete anywhere in the library. Second, where a
finding is ambiguous between a defect and an acceptable trade-off, **the
conservative reading is preferred** — v0.21.0 re-cut the default capability set
on recoverability after finding that the default profile permitted the
irreversible while forbidding the reversible, which cost compatibility and was
done anyway. Third, findings are **disclosed rather than minimised**: 0.24.0 was
yanked within one hour fifty minutes for a CSV formula-injection bug, and the
yank policy in `PROVENANCE.md` gained a category it had been missing — with the
note that the missing category was a better finding than the bug.

That commitment is why the two genuine flaws in this model are worth stating
plainly rather than softening. **T15 and T35 are both cases where a safe default
exists in the library and stops applying at the MCP boundary** — `RAW` in
every library Sheets write declaration (eight of them, across the `Backend`
Protocol, both backend implementations, and the `Sheet` façade) versus
`USER_ENTERED` in the MCP tool, and
`csv_safe` on the CSV export versus no formula handling on its `.xlsx` sibling.
They are not counterexamples to safe-by-default; they are its own test, and the
reason both are being fixed rather than accepted. The same is true of the
documentation gaps this model records: `mcp/server.py:61` describing an operator
control that does not exist, and `_export.py:200` asserting a premise that is
true one layer down. Safe-by-default only holds if the safe default is the one
that actually reaches the boundary, and the general lesson of this model is that
checking *where* a default stops applying is more productive than hunting bug
classes.

## 5. Deprioritized

| threat | reason |
|---|---|
| Spoofing of the Google API endpoints (SSRF / egress redirection) | Ruled out. All egress goes through `googleapiclient` to fixed Google endpoints; the 2026-07-22 audit specifically verified that a 403's `activation_url` is interpolated into an error string and never fetched. The allowlist host check added later is an input-validation control on operator config, not an egress control, and introduces no new egress. No URL from document content is ever requested. |
| Cross-principal session access, DNS rebinding, WebSocket origin validation, and the other `mcp`-SDK HTTP-transport advisories | Not applicable twice over. All are below the declared `mcp>=2.1` floor, and the shipped server constructs no HTTP, SSE or WebSocket transport at all — `mcp/cli.py:170` is `run(transport="stdio")`. There is no listener to rebind against and no session to ride. |
| SQL, command, LDAP, XPath and template injection | No such interpreter is reached. There is no database, no ORM and no template engine on any data path, and the one subprocess call (`demo/_feedback.py` invoking `gh issue create`) uses an absolute path from `shutil.which` with a list argv and no shell. |
| Unsafe deserialization (pickle, marshal, `yaml.load`) and eval/exec on external data | Absent from the tree. XML parsing on the Drive-sourced path uses `defusedxml`, and stdlib `xml.etree` appears only as an exception type. The residual archive-parsing risk is captured as T23 rather than dismissed here. |
| XXE and billion-laughs on the Drive XLSX export path | Empirically tested and blocked — the security audit confirmed `defusedxml` raises `EntitiesForbidden` for both. This dismissal covers only the `_cellmap` path; the unhardened `_apply.py` parser is T23. |
| Memory-safety classes — buffer overflow, use-after-free, integer overflow feeding an allocation | Not applicable. Pure Python with no unsafe blocks, no FFI and no C extensions authored here; any such defect would be in CPython or a dependency's native code, outside this model's scope. |
| Repudiation of agent-initiated mutations | Deprioritized rather than dismissed. Every mutation is attributable in Drive's own audit trail because it is performed as the authenticated user — which is exactly why attribution does not help: the log correctly names the user for an action the user did not decide. The project records that an audit log of agent-initiated mutations is an embedder obligation, and that every log call in the library is `log.warning` with no configuration. Carried into open questions. |
| Volumetric denial of service against Google's APIs | Out of scope by the project's own reasoning and by this model's. Rate limiting and cross-document pacing are explicitly assigned to the calling automation. The reportable sub-cases — unbounded decompression, per-tab read amplification, and the post-hoc download size check — appear as T23, T31 and T32. |
| Permanent deletion of Drive content | Structurally impossible in this codebase. `files.delete` and `emptyTrash` are permanently out of scope, on the stated reasoning that an agent holding full-Drive scope with attacker-influenceable input in front of it is the worst possible holder of an irreversible delete. Trash is 30-day recoverable and appears as T14. |
| Folder-scoped allowlist traversal defects (shortcut alias confusion, most-permissive-path, stale security cache, in-band self-widening) | Deliberately not implemented, with seven reasons written out in `TODO.md` so none is rediscovered mid-build. There is no folder traversal to attack. Recorded because the absence is a control, and re-introducing folders would re-open all seven. |
| Privilege escalation beyond the user's own authority | Ruled out, and it is worth stating plainly because it bounds the whole model. The credential is the user's own; every operation the server can perform is one the user could perform directly in the Drive UI or via the API. Nothing here crosses a privilege boundary upward. The threats that remain are confused-deputy threats — a third party influencing *which* of the user's own authorities gets exercised — and availability, disclosure and supply-chain threats. No row in section 4 claims escalation. |
| Reimplementing Workspace-layer policy inside this server | Out of scope by design and by correctness. For activities on Google Drive, Drive is where policy belongs: ACLs, sharing restrictions, audit logging, version history, retention, backups, Context-Aware Access and DLP, with a mature tooling ecosystem behind them. This model assumes that layer is configured (see section 1) and scores this repository's capability and allowlist model as defense in depth beneath it, not as a substitute. Recorded as a boundary, not a gap. |
| Enforcing, or compensating for the absence of, client-side tool enablement and approval modes | Out of scope, and not enforceable in principle. Which tools an MCP client exposes to the model, and whether the operator is asked to approve each call, are decided in the client's configuration. Major clients support both; the MCP specification mandates neither. The server cannot observe, verify or require them, so section 4 credits them as available controls without scoring any threat as though they are certainly applied — the same treatment given to branch protection and the PyPI publisher binding in T19. |
| Controls that belong in Google Workspace rather than in this server | Out of scope by design, and correctly so. Per-file ACLs, Drive audit logging, version history, retention and backups are the durable outer layer, and this model assumes rather than duplicates them. Recorded as a boundary, not a gap, with one asymmetry noted in section 1: those controls are detective and recoverable, so they do not bound the exfiltration rows (T4, T7) the way they bound the mutation rows. |
| Elevation of privilege through the in-band tool surface | Ruled out structurally. No tool mutates the policy; `Policy.with_enabled` is configuration-only; `_GATES` fails closed on any `Backend` method it does not name; unknown capability and profile names are hard errors rather than silent narrowing; and a typo'd profile errors rather than falling back to something wider. The model cannot widen its own authority. The bypasses that do exist are all out-of-band: the operator's config (T1), the raw library seam (T11), and a sibling connector (T10). |

## 6. Open questions

Questions the code could not answer. Struck-through items were answered by the maintainer on 2026-08-27 and are retained so the reasoning behind the scoring stays auditable.

- ~~**Is `ALLOWLIST_READ='*'` a permanent posture or a migration state?**~~ **Answered:** a migration state. The 1.0.0 plan has operators set the value at install time; the mechanism for that is still being designed. T1 rescored to `risk_accepted` and reframed as a blast-radius modifier on T2 rather than an independent critical threat.
- ~~**Was the release job's single-job structure a decision or an accretion?**~~ **Answered:** a known-temporary posture during rapid pre-1.0 development. T3's rating held; see its controls cell for why the internal framing does not fully bound it.
- ~~**Deployment reality — who runs this today?**~~ **Partially answered:** the wide-open read posture is a CSA-internal deployment with known operators. Still open: how many operators, and whether any external party has installed the public PyPI package.
- ~~**Do clients offer the operator any control over approval?**~~ **Answered:** yes — approve-every-action, allow-for-this-project, and always-allow are all available, and approve-every-action fully mitigates T7. Recorded as a control on T7 and as an assumption in section 1. Still open, and now the highest-value question: **which mode do real operators actually run, and what does each client do with `readOnlyHint` in the non-strict modes?** The spec maps `readOnlyHint: true` to "skip the confirmation dialog" for a trusted server, and a locally-installed server is the trusted case — so the finding turns entirely on whether any deployment uses a mode that honours it.
- **Which tools are actually enabled in the deployed client configurations, and which approval mode is set?** Both are operator-side controls this repository cannot read, and together they determine the real residual for T7 and most of the mutation rows. If `export_comments` is disabled in the deployed configs, T7 is closed in practice today and the annotation fix becomes hygiene rather than remediation. Worth capturing as part of the 1.0.0 install-time configuration work.
- **Is the Workspace-layer assumption actually true for the operators?** Section 1 assumes Drive is secured such that neither the user nor an AI acting for them can take unsanctioned action. Has anyone verified the sharing restrictions, audit-log retention and backup coverage for the accounts this is installed against? Every rating below inherits that assumption.
- **What Workspace edition do the operators actually have?** T4's rating now depends on it: DLP for Drive requires Enterprise Standard or Plus, Frontline Standard or Plus, Education Standard or Plus, or Enterprise Essentials Plus, and real-time blocking is Enterprise-tier. Below those editions T4 has no preventive outer control.
- **Is an autonomous-sweep deployment running now?** `SECURITY.md` names it the higher-risk use case (no human in the loop, ingesting comments from many documents). Design-stage or live? This decides whether the LLM map-reduce mitigation is urgent or speculative.
- **Is `export_comments(destination="file")` used in practice, and by whom?** If the local-write path has no real consumer, deleting it closes T7 outright — cheaper and stronger than gating it.
- **Whose Drive is at risk today?** Does any operator hold Workspace admin rights, which would widen T6 from "their own Drive" to org-wide content?
- **Does the real workload include documents shared *to* the user by external parties?** T2's likelihood turns on this. Internal-only documents authored by colleagues is a materially different exposure from files shared inbound by anyone.
- **Which of the seven objections to folder-scoped allowlisting have changed?** Folder support is planned, and `TODO.md` argues against it in seven specific ways — shortcut alias confusion, most-permissive-path on multiple parents, a stale *security* cache meaning a revoked grant still works, and in-band self-widening when the agent creates a file inside an allowlisted folder. Which of these is now considered solved, and how?
- **Are the external controls actually in place?** Is the PyPI Trusted Publisher binding constrained to the `pypi` environment; does that environment still have required reviewers after the removal noted in v0.21.0; does branch protection on `main` currently require status checks? None is verifiable from the repository — T19 exists because of that.
- **Is there a runbook for suspected token compromise?** T5 and T21 both rest on the token being unrevocable from within this codebase.
- **Does any deployment enable the `full` profile?** T4 and T20 are scored assuming `file.share`, `comment.edit` and `comment.delete` stay off.
- **Is a re-audit of the post-v0.1.0 surface planned?** Both prior audits cover v0.1.0 while HEAD is ~v0.28.0; `mcp/`, `policy.py`, `allowlist.py`, `_apply.py` and `_export.py` have never been externally reviewed.
- **Risk appetite on availability.** Is T30 (auth-flow denial by any local process) worth fixing, or is "re-run `authenticate`" an acceptable answer?
