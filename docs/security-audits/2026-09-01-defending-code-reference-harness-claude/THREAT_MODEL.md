## 1. System context

`csa-google-workspace` is a Python library and MCP server that gives an LLM
read and write access to Google Docs, Sheets, Slides, and Drive comments. It is
installed locally by an operator, authenticates as a real end user through an
OAuth loopback flow, and holds a persisted refresh token carrying full-Drive
scope plus the three editor scopes and a read-only labels scope. At `d33034b` it
exposes **50 MCP tools** across 57 modules and 12,266 lines of `src/`.

The security surface is not the library's own memory safety; it is the
deployment model. The server is a **deputy**: it holds the user's authority and
acts on instructions that arrive, in part, from documents and comments written
by other people. `SECURITY.md:3-6` states this directly — *"That deployment
model, not the library's own code, is where the real security surface lives"* —
and the design spec sharpens it to the useful form
(`docs/superpowers/specs/2026-08-28-capability-model-mirrors-drive.md:29-31`):
*"the model constrains the deputy, not the principal … the delta is never
capability, it is **who decides**."* Every operator of this server already has
the access it exercises. What the server adds is a path by which a third party's
text can cause that access to be exercised.

**The posture this model is written against.** Four independent ceilings exist,
and an operator can narrow each: 11 named capabilities (with five ascending
profiles), a per-file read allowlist, a per-file modify allowlist, and — new
since the prior audit — a tool-surface ceiling (`CSA_GW_FLAVOUR`) that removes
tools from the live registry at startup. Two local-I/O switches and a log level
sit alongside them, 14 environment variables in total.

**A default install narrows none of them.** Since `f481733` (v0.31.0) every
capability is enabled, including all four irreversible ones
(`comment.edit`, `comment.delete`, `content.delete`, `file.share`), and both
allowlists permit every file the credentials can reach. This is a recorded
decision, not an oversight: Drive owns sharing policy, the capability layer
constrains the deputy rather than the principal, and the documentation's job
becomes *how to narrow this* rather than *how to switch it on*
(spec `:213-215`). `SECURITY.md:107-109` states the consequence without
flinching — *"a default install carries no capability-level mitigation"* against
the project's own named primary risk. The controls that survive by default are
therefore: no permanent delete exists anywhere in the backend; a typo'd profile
is a hard error; a malformed allowlist refuses everything rather than widening;
`type="anyone"` link-sharing is structurally unreachable; `owner` is refused on
every grant path; Drive labels cannot be written at all; and Drive's own ACLs,
which back-stop everything above.

Scoring below is **residual after those controls**, on a default install, because
that is what most operators will run.

## 6. Open questions

Questions the code could not answer, for a human owner. Prior-model questions
that the tree has since answered are omitted.

- **Is the fully-open default the intended 1.0.0 shipping posture, or does the
  install-time configuration step still exist in the plan?** The living model's
  §6 says operators will set the value at install time; §0 rescores T1 on the
  basis that the open default is permanent. These cannot both be current, and
  which one is decides whether T1 stays `risk_accepted` (see F3).
- **Should re-parenting be gated as a sharing operation, or should the ladder
  claim be withdrawn?** T38 is a genuine design fork, not a bug with one right
  answer. Gating preserves the Drive-mirroring claim at the cost of making
  `writer` unable to organise files; withdrawing it keeps `writer` useful and
  makes Drive's folder ACLs the control. The audit has no basis to choose.
- **Is `clear_cells` intended to be `content.delete`?** F1 assumes yes, on the
  strength of `policy.py:194`, `test_demo.py:365-370`, and the stated purpose of
  the capability. If the answer is no, then four artefacts and two tests need
  changing instead of one line — and the capability's boundary needs restating.
- **Are the three hardcoded Drive-shaped ids real?** F25 reports them by shape
  only. The answer changes this from a one-line comment to an 18-file sweep.
- **What is the intended retention for the client-side MCP log?** The server
  documents that it cannot purge it (`_logging.py:1-21`). Whether that is
  acceptable depends on the operator's environment, and no guidance exists.
- **Does any operator run with a narrowed posture today?** The whole capability
  layer's value is conditional on it being used. `preview_allowlist` exists to
  make narrowing checkable, which suggests the intent is real, but nothing in
  the tree indicates adoption.
- **When `CONTROLS_TOKEN` expires on 2027-09-01, what fails and how loudly?**
  `check_controls.py` is the only assertion of externally-enforced controls, and
  its weekly runner currently cannot fail for an unrelated reason (F12).
